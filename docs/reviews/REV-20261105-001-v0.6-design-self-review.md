## 总体判断

继续推荐自建 StateGraph 调度主流程、LangChainModelPort 实现 ModelPort。现有 ContextService、
ToolRuntime、EventJournal、SessionRecovery 和 MemoryStore 保留事实与业务职责。这能分别检验
流程改造与模型接入，避免同时更换权限、历史和恢复规则。

原方案已经说明不使用持久图恢复、不自动重试副作用、工具按顺序执行、流尾 Usage 不能遗漏、
取消要完成清理，也说明了引用修复与普通请求的差异。本次不把这些已写明的限制再次列为发现。
需要补齐的是几个容易在实施时误解的现有行为，以及新后端真正参与验收的证据。

## 发现与建议

### F01：Live 总预算入口只覆盖旧模型适配器

- **finding_id**：`REV-20261105-001-F01`
- **severity**：`high`，在执行新适配器 Live 验收前必须解决。
- **location**：[设计](../architecture/v0.6-langchain-langgraph.md)第 282、315、321–322 行。
- **claim**：A13 要求固定调用和 token 总预算，并把既有 Live 测试作为起点，但没有说明预算拦截器
  如何迁移到新适配器。仅把运行配置切成 LangChain，会绕开现有测试的专用总预算包装。
- **evidence**：[test_v05_context_live.py](../../tests/integration/test_v05_context_live.py)第 52–87 行
  只替换 `DeepSeekModelPort.stream`；第 60–64 行的跨尝试总调用数与 token 检查都在该包装内部。
  新的 LangChainModelPort 不会自动经过这个具体类的方法。产品自身费用账本不等于这份实验总额度。
- **impact**：新后端可能仍受产品预算约束，却没有执行实验约定的总额度检查；两边结果也无法用同一
  总账核对。这是未来直接复用现有测试的风险，本轮没有执行 Live，也没有发生新后端超额调用。
- **recommendation**：在 P0/P4 明确增加与具体适配器无关的实验预算包装，包住选中的 ModelPort，
  覆盖任务、压缩、引用修复及实验启用的维护请求。每次发送前记录预留，缺失 Usage 时保留预留。
  先用假 HTTP 验证新旧适配器在预算耗尽时均不发送请求，并核对真实底层尝试数；保留关闭 SDK
  重试的原要求。通过这项离线验证后，才允许进入 A13。

### F02：模型配置逐轮重载与客户端复用的关系未写明

- **finding_id**：`REV-20261105-001-F02`
- **severity**：`medium`。
- **location**：[设计](../architecture/v0.6-langchain-langgraph.md)第 225、243–245、287–292、312 行。
- **claim**：设计要求保留模型参数并管理客户端生命周期，但没有区分“后端选择需重启”和现有
  `model`、timeout、输出上限逐轮重载的行为，也没有规定复用的模型对象怎样应用请求快照。
- **evidence**：[Coordinator](../../src/jdagent/application/coordinator.py)第 238 行每次发送前调用
  `prepare_turn()`；[composition.py](../../src/jdagent/composition.py)第 165–170 行要求 Provider、
  base_url 等变化时重启，第 182–187 行则更新 model 与请求设置，第 199–202 行更新维护模型。
  [DeepSeek Adapter](../../src/jdagent/adapters/deepseek.py)第 75、94–97、186 行使用每份请求里的
  model、输出参数和 timeout。[现有配置测试](../../tests/test_v05_runtime_configuration.py)
  只覆盖初始窗口和归档，不能证明第二轮重载继续有效。
- **impact**：若新 Adapter 只在构造时固定模型与设置，后续归档可能描述新模型，实际请求却仍使用旧
  配置；若靠修改共享对象更新设置，还可能影响已建立的其他请求。这是待实现选择造成的条件性风险。
- **recommendation**：补充合同：后端标识在进程内固定；每个 ModelRequest 是模型和请求设置的权威
  快照。新 Adapter 可以复用传输资源，但不能把请求参数隐式固定为启动值，也不能修改已建立请求
  的配置。将“同一进程两轮之间改变 model、timeout、max_output_tokens，归档与捕获的 HTTP 请求
  均使用各轮值”加入 A10；维护请求也按它自己的快照发送。具体缓存方式留给 P0 实验决定。

### F03：工具调用 ID 去重需要区分响应、当前 Turn 和既有 Session

- **finding_id**：`REV-20261105-001-F03`
- **severity**：`medium`。
- **location**：[设计](../architecture/v0.6-langchain-langgraph.md)第 143–150、186–188、226、304 行。
- **claim**：重复 ID 在设计中出现多次，但未说明去重范围及其所有者。新 Adapter 能验证单次响应，
  无法独自实现旧 Loop 对 Session 历史的检查；图状态表也没有交代该检查所依赖的状态。
- **evidence**：[loop.py](../../src/jdagent/core/loop.py)第 134–139 行在 Turn 开始时从 Journal 中
  所有已保存的 assistant 工具列表初始化 `seen_call_ids`，第 475–477 行检查本次响应内及已见 ID，
  第 537 行在逐项发起工具前补入当前调用。当前批次因新目录规则而跳过的后续调用不会在这一步加入。
  [已有重复 ID 测试](../../tests/test_agent_loop.py)第 156 行起只构造同一响应内的重复 ID。
- **impact**：只做 chunk 聚合后的去重会放过跨 Turn 重用 ID；反过来，每轮模型调用前都重建整个
  Journal ID 集合，也会改变旧 Loop 对当前 Turn 中已跳过调用的处理。两种实现都可能通过现有单批测试。
- **recommendation**：在图的运行状态说明中补充运行期 ID 集合或等价机制，写明从 Journal 初始化的
  时点和逐项更新时点。A01/A02 增加上一 Turn 重复 ID、同一 Turn 后续响应重复 ID，以及新规则导致
  剩余调用跳过后的复用场景。历史检查由 Runner 负责；若决定统一为更严格的会话唯一规则，应作为
  明确纠偏单列，不能在等价迁移中静默改变。

### F04：工具次数不是简单的实际执行次数

- **finding_id**：`REV-20261105-001-F04`
- **severity**：`medium`。
- **location**：[设计](../architecture/v0.6-langchain-langgraph.md)第 146、189–190、206、303、306 行。
- **claim**：方案要求保持计数与调用限额，却没有展开新目录规则中断批次时的特殊计数。把图节点的
  工具次数定义为“调用 execute 的次数”，会改变现有行为。
- **evidence**：[loop.py](../../src/jdagent/core/loop.py)第 556 行对当前返回的工具计数，遇到
  `INSTRUCTIONS_DISCOVERED` 时，第 563 行还加上本批剩余调用数，随后将它们补成 `not_executed`。
  该计数继续参与第 527 行的限额检查。[目录规则测试](../../tests/test_v05_instructions.py)
  检查了补齐结果和未写入文件，但未断言返回计数及后续限额行为。
- **impact**：例如两项工具因第一项发现规则而结束本批时，旧结果计数为 2，虽然第二项未进入执行。
  新图若记为 1，就可能给后续规划多一次工具额度，也会破坏 A01 要求的 TurnResult 和事件差分。
- **recommendation**：把“业务工具计数”与“实际工具执行次数”分开说明，不增设第二份持久账本。
  A03/A04 增加两项批次、首项发现新规则、剩余项补齐、随后继续规划的边界场景，核对计数与停止点。
  如果认为旧计数不合理，应单列行为修改；首轮框架迁移不要顺便修正。

### F05：四种组合和默认切换的验收安排仍不够具体

- **finding_id**：`REV-20261105-001-F05`
- **severity**：`medium`。
- **location**：[设计](../architecture/v0.6-langchain-langgraph.md)第 278–293、301–328 行。
- **claim**：方案提出检查四种组合，但没有明确每组必须执行哪些验收、怎样证明选中了预期后端。
  Fake Provider 明确绕开两个真实模型适配器，因此引擎 Fake 差分通过不能证明新 Adapter 与图的组合通过。
- **evidence**：设计第 289 行保留 FakeModelPort，第 293 行要求四组合；现有
  [v0.4 Live](../../tests/integration/test_v04_tools_live.py)第 47–59 行和
  [v0.5 Live](../../tests/integration/test_v05_context_live.py)第 104–117 行均从当前默认组合根构建，
  尚无引擎／适配器参数。现有测试文件在方案中只是起点，不能直接视为覆盖了新路径。
- **impact**：测试可能大部分仍运行旧 Loop，或只测到新图加 Fake；组合接线、CLI 选项与客户端
  关闭问题直到默认切换后才出现。“每个后端三次”也容易被理解为两组或四组不同的实验总量。
- **recommendation**：在 P0 固定一份可执行矩阵，明确每项由测试构造参数选择后端，并记录实际生效值。
  推荐最小安排如下；它是待纳入方案的建议，不是本轮测试结果。

| 验证层次 | 必须覆盖的组合 | 重点 |
| --- | --- | --- |
| 引擎确定性差分 | native/Fake、langgraph/Fake | A01、A03–A09 的适用场景，比较请求、事件、计数与副作用 |
| 适配器协议 | native Adapter、LangChain Adapter，均使用假 HTTP | A02、A07、A10；重载、结束证据、Usage、重试、预算阻断 |
| 组合根集成 | native/native、native/langchain、langgraph/native、langgraph/langchain，均使用假 HTTP | 真实接线、工具往返、压缩与修复、取消、资源关闭、恢复及 CLI 选择；关键公共场景四组都跑 |
| 真实任务对照 | 初始 native/native 与目标 langgraph/langchain，各三次 | A13；两种混合组合先用离线证据定位问题，需要时另列有明确额度的 Live 实验 |

“延迟／费用明显上升”也应在执行对照前转成记录好的判据：比较哪些指标、容忍范围如何依据基线确定、
超过范围如何处置。当前没有实测依据，不建议在自审中随意填一个百分比；三次任务也不足以作稳定的
性能统计结论。硬性任务失败和超出实验预算仍直接判失败，不被平均值抵消。
