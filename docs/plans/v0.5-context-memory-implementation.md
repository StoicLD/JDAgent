# v0.5 实施计划

状态：`Proposed`

日期：2026-10-21。[产品范围](../requirements/v0.5-context-memory.md)已确认；本计划细化工程步骤，
尚未授权修改产品代码。每阶段交付可验证的纵向能力，不先搭建空壳框架。
修订：2026-10-22，R1；[Cursor 审查处置](../reviews/REV-20261021-001-v0.5-context-memory-design-review.md)
已逐项补入设计，独立复审与实现授权仍待完成。

## 实施前条件

先评审[架构](../architecture/v0.5-context-memory.md)、[ADR-0007](../decisions/ADR-0007-context-projection-memory.md)、
[验收方案](../development/v0.5-context-memory-validation.md)的新增存储和限额提案。
在固定 revision 上建立无新能力基线；学习者补充候选比较与故障预测，不能追写成原始认知。

v0.4 真实执行遗漏和学习出口仍未关闭，v0.3 也有工程遗留。此次设计确认不豁免现有门禁：
实施前对 Session 恢复、Tool Runtime、模型调用、KB 来源生命周期相关缺口做依赖核对；其余 RAG
质量问题继续独立记录。若要提前实施，须有明确的范围裁定，不能沿用只适用于 v0.3→v0.4 的旧例外。

## 阶段一：上下文与原文基础

交付一条从用户输入到可追溯模型请求的完整链路：新 Session 格式、原文对象、RequestManifest、
指令版本与路径发现、Provider/model 配置、统一预算和 `/context-window`。

- 复用现有 Loop/Session/ModelPort；消除输出预留硬编码，未知容量有明确错误。
- 完整结果先存档，再生成有界预览；工具调用与结果不拆开。
- 配置与已知指令在 Turn 边界重验，新目录写入前能先返回新规则。
- 区分目录发现缓存与本轮活跃规则；总预算采用统一 E，显式映射应用上限和模型容量，已知模型
  档案须核对官方来源，未知容量有启动错误。不得沿用校准显示值与原始字节硬门槛的双重口径。
- 固定 recovery 引用字段、Session OS 独占锁与 manifest 对象/事件引用布局，持续追加不反复全量
  解析；引入单一终端输入所有者，为运行中命令与审批路由建立可测合同。
- 将“仅滑窗删除历史”标为待替换路径，阶段一不可宣称长任务能力已经完成。

退出条件：AC-02、03、04、05 的统计部分通过；请求清单可重建；规则变化、缺失、越界与超大固定
内容均有确定结果；不改变工具权限。旧会话已于 2026-10-21 完成一次性过渡，本次修订与实现阶段均不重复扫描删除。
E26、E28、E30、E31、E34 的基础部分通过；新增 Memory 授权不放宽现有文件或命令权限。

## 阶段二：压缩、排队与恢复

交付同一 Turn 多次压缩并完成任务：保护原文、结构化分段摘要、近期批次、压缩事务、手动命令和
恢复。Loop 只协调安全边界，压缩模型不执行任务工具。

- 先用 Fake Model 确定摘要状态与提交点，再验证真实模型的语义质量。
- 覆盖 90% 触发、40% 软目标、超大结果分段、无缩小、失败、取消和预算耗尽。
- 在候选落盘前后、提交前后、工具副作用与结果持久化之间注入故障。
- 正常压缩等待已发出批次闭合，不取消剩余调用；新规则、取消等例外保留具体停止原因。
- 超大参数和结果先归档，以整个闭合批次进入摘要；实现保护区超限诊断和不依赖模型的直接撤销
  输入。保留默认 16/32/2 并允许显式配置，控制结果不算 observed_failure。

退出条件：AC-01、05、06、10 的压缩部分通过；重复压缩不丢禁令，恢复无重复副作用；已记录
与旧滑窗基线的完成率、错误、token、成本和延迟差异。此时仍不能将 v0.5 整体标为完成。
E25–26、E32–33 的恢复、输入和大批次部分通过；“至少三次”仅为 E01 提案参数，不回写为已批准产品数字。

## 阶段三：历史检索与记忆生命周期

交付同 workspace 跨会话关键词/语义检索、逐轮有效记忆召回、自然语言查看/更正/停用，以及首轮后
后台两阶段整理。保存 provenance、版本、水位、停用约束与恢复作业。

- 先构造两个 workspace 和用户作用域的固定来源，验证过滤先于排名。
- 提取与合并分开计费、幂等提交；包括空结果、来源变化、无变化不调用、并发触发和重启。
- 稳定偏好、一次性任务、错误陈述、显式更正和重复改写分别测试。
- 验证 KB 与 Memory 的来源生命周期不同，不能通过新存档绕过知识删除。
- 明确直接用户意图、自动维护策略、Memory 权限 target 与写入版本校验；Headless 可处理明确意图，
  无法询问的含糊操作拒绝或待澄清；项目作业不能提升用户作用域或复活停用项。
- 交互与 Headless 首轮都登记任务，启动即续跑旧待办；补有界退出、显式待办维护入口、费用预留和
  epoch 过期提交拒绝，不能把“已排队”当“已完成”。

退出条件：AC-07、08、09、10 全部通过；无数据时不注入，停用记录不复活，语义服务故障可见；
双路检索都有真实证据，不能只用 Fake 或关键词降级宣称阶段完成。
E27–29、E35–36 及 E22/E23 的扩展场景通过，演示快速退出后真实完成待办的路径。

## 阶段四：联合验收与学习出口

以固定 revision 和配置运行[验证矩阵](../development/v0.5-context-memory-validation.md)，记录离线
确定性结果、真实模型逐次结果、成本与失败分类；不通过时保留失败样本再修复。
F13 的缓存布局优化在此以基线比较决定；单独报告 cached_tokens 和 Provider 缺测状态，不因优化
重新排序工具配对或提高 Memory 指令优先级。

退出条件：AC-01–11 均有证据；与实现前基线比较；相称独立评审闭环；学习者完成闭卷、故障判断与
延迟复测。分别报告工程状态和学习状态，并同步 Map、模块现状、README 与当前状态。

## 实施顺序与可并行边界

主链为阶段一→二→三→四。阶段一合同稳定后，测试数据整理与只读参考核查可以独立进行；共享
Session 格式、提交协议和预算计算必须由一个写入者统一维护。不得让两个实现同时修改主循环与
同一持久状态。临时夹具不写入用户真实历史，故障实验使用专用目录。
