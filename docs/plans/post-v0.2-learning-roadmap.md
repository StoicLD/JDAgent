# v0.2 之后的模块学习路线

状态：`Approved`

批准日期：2026-08-24

路线调整日期：2026-09-16，项目所有者决定将 Tool Registry & Function Calling 提前到 v0.4，
长期记忆与 Context Orchestration / Compaction 按原相对顺序顺延至 v0.5、v0.6。

批准范围：本文件批准学习优先的推进方式、v0.3–v0.6 的先后方向和开始下一模块的门禁，不批准
任何尚未形成的版本需求、具体技术方案、依赖或实现。每个版本仍需分别批准需求、架构、实施计划、
Eval 和学习清单。

## 总体方向

JDAgent 的长期功能参照是具备成熟 Coding Agent 的基本能力，但功能数量不是首要成功标准。后续
模块以形成可迁移的 Agent 工程能力为主线，同时产出：

1. 一个可工作的端到端产品能力；
2. 明确的需求、边界、Interface、Trade-off 和失败模型；
3. 实现前基线、实现后 Eval、故障实验和评审证据；
4. 学习者能够闭卷重建并应对陌生变体的心智模型；
5. 可用于求职展示但不夸大生产经验的工程材料。

详细角色、产出和门禁见[模块交付与学习工作流](../development/module-delivery-workflow.md)。

## 已批准的近期顺序

### 已解除门禁：v0.2 M10

项目所有者于 2026-08-24 明确决定，CLI/UI 不属于当前最优先的 Agent 核心学习内容，因此
[v0.2 CLI 人工学习检查表](../learning/v0.2-learning-checklist.md)不再要求逐项执行，v0.2 学习
门禁按范围裁定关闭。当前可以直接开始 v0.3 的思考、需求和设计计划；这项一次性裁定不放宽
v0.3 及后续核心模块的学习门禁。

### v0.3：RAG 与来源可追踪的知识检索

核心结果：JDAgent 能从小型、有明确来源的知识库检索证据，在预算约束下把证据注入模型请求，
并保留回答与来源的可核验关系。

设计必须覆盖：知识与来源模型、摄取和 Chunking、至少两个可比较检索基线、排序与过滤、Context
注入、引用、索引恢复、空/错/重复/过期结果，以及 Retrieval 与 Answer Eval。

边界：首版优先固定本地语料和可人工检查的数据集；网页采集、求职领域包、自动长期记忆、分布式
向量存储、多模态和复杂 Agentic RAG 不自动进入 v0.3。

### v0.4：Tool Registry & Function Calling

核心结果：在已有工具调用闭环上扩展系统可调用的实用工具，并明确统一的工具定义、注册、模型
暴露、执行和结果回传边界，使后续 Memory、Context 与 MCP 能复用工具基础能力。

当前基线：v0.1 已实现 `ToolRegistry`、`ToolDefinition`、JSON Schema 参数校验、权限审批、
超时与错误归一化，以及 `calculator`、`read_text_file`、`write_text_file`；ModelPort、Agent Loop
和 Session 已支持 Tool Call / Tool Result 闭环。v0.4 的增量是扩展工具能力并完善这些边界。
事实依据见[Runtime 核心契约](../architecture/runtime-contracts.md)、
[ModelPort 设计](../architecture/model-port.md)与[工具运行时](../../src/jdagent/tools/runtime.py)。

设计必须覆盖：

- 新增工具解决的具体任务、输入/输出与调用示例；目录浏览、文件查找、文本搜索和局部编辑可作为
  候选比较，最终工具清单与命名在 v0.4 需求中确定，不在路线中冻结。
- 工具定义、名称冲突、注册与装配、可用工具集合及 Schema 导出；明确 Registry、Tool Runtime、
  ModelPort、Agent Loop 与各 Handler 的职责和依赖方向。
- Function Calling 的完整数据流：Schema 发给模型、流式参数组装、完整调用校验、执行、结果
  回传及后续模型调用；覆盖未知工具、参数错误、重复 call ID、多调用顺序和调用预算。
- 权限与 workspace 边界、审批、超时、取消、副作用不确定性和重试条件，复用现有 Session
  恢复与事件合同；明确错误和结果大小限制，以及哪些结果信息供后续 Context 模块使用。
- 最小 Tool Eval：现有三工具基线、新工具端到端任务、工具选择与参数正确性、失败反馈、权限
  拒绝与取消、结果关联、成本与延迟；确定性 Fake 场景与真实 Provider 验证分别取证。

边界：v0.4 不交付长期记忆生命周期、完整 Context 编排/压缩或 MCP 协议接入。Shell、进程、网络、
动态插件和并行工具执行不因本次提前而自动纳入。工具扩展必须由真实任务证明，不为未来模块创建
空壳 Port 或框架；不改变 v0.3 知识管理 CLI 不注册为模型工具的既有边界。

对后续模块的帮助与职责划分：

| 后续模块 | 可复用的工具基础能力 | 仍由该模块定义和持有的职责 |
| --- | --- | --- |
| v0.5 Memory | 若开放记忆工具，复用注册、Schema、权限、调用与结果合同 | 记忆作用域、写入理由、冲突、遗忘与删除 |
| v0.6 Context | 工具 Schema 与结果的大小、关联信息、失败和预算约束 | 多来源选择、配额、摘要与压缩；不要求压缩本身成为工具 |
| MCP（候选） | 将外部工具适配到经过验证的注册与执行边界 | 协议、连接生命周期、工具发现与外部信任边界 |

### v0.5：长期记忆生命周期

核心结果：JDAgent 能在明确作用域、来源和用户控制下形成、读取、更新、冲突处理、遗忘和删除长期
记忆；记忆不会被误认为不可变 Session 历史，也不会泄漏到错误的 Session 或 workspace。

设计必须覆盖：记忆类型和作用域、候选生成、写入与批准策略、来源与置信度、Recall、冲突与合并、
过期与遗忘、查看修改删除、污染与 Prompt Injection，以及 Memory Eval。

边界：长期记忆不是把 v0.3 Knowledge Base 改名为 Memory。外部知识强调来源和版本；长期记忆
强调写入理由、修正、遗忘、隐私和用户控制。两者只有在实现证明存在真实共同变化点时才共享内部
seam。

### v0.6：Context Orchestration 与 Compaction

核心结果：JDAgent 能在 System Instructions、当前输入、Session 历史、Tool 结果、RAG 知识和
长期记忆之间进行可观察、可解释的预算分配、选择和有损压缩。

设计必须覆盖：来源优先级、Token Budget、滑动窗口、摘要、受保护信息、Tool 结果压缩、RAG 与
Memory 配额、压缩触发、来源与丢失诊断、Prompt Caching，以及质量、成本和延迟 Eval。

v0.3 RAG、v0.4 Tools 和 v0.5 Memory 只实现各自端到端结果所需的最小 Context 注入与结果边界；
完整多来源编排留给 v0.6，避免 RAG、Tools、Memory 和 Context 的职责提前混合。

## 2026-09-16 路线调整与启动边界

- 改变依据：项目所有者明确要求 v0.4 优先推进 Tool Registry & Function Calling，增加系统可调用
  的工具和模块设计，为 Memory、上下文压缩、MCP 提供基础。
- 顺序影响：原 v0.4 Memory 顺延为 v0.5，原 v0.5 Context 顺延为 v0.6；MCP 继续作为后续候选，
  未分配版本号。v0.1–v0.3 的历史范围和验收记录保持原含义。
- 待验证假设：先用真实工具任务检验注册、执行与结果边界，可以减少后续模块重复建设；是否共享
  Interface、采用何种结果表示，由 v0.4 方案比较与实验决定。
- 当前动作：按用户本次决定进入 v0.4 的初始模型、需求与设计准备；具体设计包尚未形成，不将
  路线调整记为实现授权或设计包批准，也不代填学习者初始模型。
- v0.3 学习出口已关闭，但工程复核仍未通过，详见[当前状态](../context/current.md)。v0.4 设计
  需识别依赖的 v0.3 缺口；进入实质性实现前，按现有门禁核对工程状态，若仍有未关闭项，须由
  项目所有者明确裁定其对 v0.4 的阻塞范围。此次排序调整不代表 v0.3 工程验收通过。

## 必须保持不同的事实

| 事实类别 | 含义 | 主要所有者与不变量 |
| --- | --- | --- |
| Session Event | 已发生的运行历史 | append-only 规范事件；用于恢复和审计 |
| Knowledge | 外部来源支持的知识 | 随来源版本更新；强调证据和引用 |
| Long-term Memory | 从交互形成的持久信息 | 可修正、遗忘和删除；强调作用域和用户控制 |
| Context | 单次模型调用实际看到的投影 | 每轮构建；受预算、优先级和选择策略控制 |

任一版本不得让同一事实由两个模块独立持有，也不得用摘要、检索结果或模型推断覆盖规范 Session
历史。

## Eval 的位置

Eval 不单独占用一个产品版本，而是从 v0.3 起成为每个模块的强制横向门禁。每个模块必须包含：

1. 固定且可检查的场景或数据集；
2. 未增加新能力时的实现前基线；
3. 与核心结果匹配的指标和失败分类；
4. 实现后对照与失败样本分析；
5. 至少一个由学习者先预测、再实际制造的故障；
6. 关键回归的自动或人工门禁。

## 后续候选方向

以下内容仍是候选，不批准版本号、顺序和范围：

- 安全 Shell、进程执行与 Project Trust；
- MCP 与外部 Tool Ecosystem（在 v0.4 工具边界得到验证后评估接入，版本与顺序待定）；
- Project Instructions、Skills 与 Hooks；
- Subagent 与任务编排；
- 求职领域包及领域 Eval。

选择后续方向时，根据 v0.3–v0.6 的实际接口、学习结果、目标岗位证据和产品需求重新排序，不因
Claude Code 拥有某项功能而自动立项。

## 路线变更规则

- 当前模块的工程和学习门禁未通过前，不启动下一实质性模块。
- 新证据可以改变顺序，但必须记录改变的事实、假设和影响。
- 路线只说明“为什么先学什么”；具体版本文档必须回答“交付什么、如何验证、为什么这样设计”。
- 路线不得被用来预创建包、Port、配置、依赖或空壳代码。
