# v0.4 工具执行层设计讨论

状态：`Proposed`

开始日期：2026-09-20

访谈收敛日期：2026-09-23，共 23 题。单题取舍已逐项确认，汇总设计及 AI 建议默认值待整体审阅。

本文记录项目所有者逐题讨论中的候选方向、已确认取舍和待决问题。单题结论不表示整个需求、架构
或实施计划已获批准；当前只讨论和记录，不实现产品代码。收敛后形成范围、模块边界、核心契约与
验收方案。既有路线见[模块学习路线](post-v0.2-learning-roadmap.md)。

访谈方式：项目所有者于 2026-09-20 将“每轮一题”调整为可合并独立问题；每轮 3–4 题，目标约
20 题，总数包含 Q1、Q2 在内不超过 30 题。依赖尚未确定答案的问题留到后续轮次；已明确的
约束直接记录，不以重复提问或未编号子问题扩大数量。

## 项目所有者给出的初始方向

- 目标：复用 ToolRegistry、ToolRuntime、权限审批与 Session Event，完善可控、可扩展的工具
  执行层；保持模型无关，新增工具不修改 AgentLoop。
- 候选能力：文件发现、分段读取、文本搜索、创建文件、精确编辑；命令执行分阶段开放，先明确
  审批、隔离和进程管理。具体工具清单与契约尚未确认。
- 重点：工具描述、参数与结果；已注册、本轮可用、获准执行的区别；路径校验、覆盖保护、修改
  冲突、输出限制、超时取消与进程清理。
- 约束：副作用不确定时不能盲目重试；工作目录限制不能视为沙箱。
- 暂缓：MCP 接入、多版本治理、动态工具发现、多 Agent、长期进程交互。MCP 按跨系统互通
  需求选择，不按工具复杂度划分。
- 候选验收主线：找文件 → 读取搜索 → 精确修改 → 运行验证 → 报告实际结果，并覆盖失败路径。

## 当前代码基线

核对 revision：`21a5aa4066dc0ea318f8949b8c0bd8cc4e62c909`。以下为代码与现有测试的静态核对，
本次未运行测试，不构成新验收证据。

- [AgentLoop](../../src/jdagent/core/loop.py) 通过 `ToolRuntimePort.execute()` 串行分派工具，
  没有按工具名分支；请求与结果写入规范事件。
- [Composition Root](../../src/jdagent/composition.py) 将 Registry 全量定义交给 ContextBuilder；
  [ToolRuntime](../../src/jdagent/tools/runtime.py) 按注册名称查找，再校验参数与权限，没有独立的
  本轮可用工具集合执行门禁。
- [内建工具](../../src/jdagent/tools/builtins.py) 仅有计算器、全文读取与整文件写入。写入允许
  覆盖，无修改冲突检查；没有本轮候选的文件发现、搜索、精确编辑或命令执行能力。
- [工具类型](../../src/jdagent/domain/tools.py) 的 Handler 返回字符串，ToolResult 有通用
  metadata，但尚未定义截断、冲突、进程结果或副作用状态合同。
- 现有审批与 Session 允许规则主要围绕文件路径；审批摘要将非路径字符串表示为字符数，不能
  直接承担待设计的具体命令或编辑内容展示。
- 文件 I/O 通过 `asyncio.to_thread()` 执行；Runtime 的 Handler 超时与取消不能据此证明底层
  写入已停止。[现有控制测试](../../tests/test_runtime_controls.py) 使用可取消的异步等待，
  未证明线程写入或未来进程已停止。

## 逐题结论与待决项

### Q1：v0.4 是否必须由 Agent 执行真实验证命令

- 用户选择：A，必须；确认日期为 2026-09-20。
- v0.4 最终验收包含 Agent 自己执行真实验证命令并获取结果；仅给出命令建议、交由用户执行，
  不满足这条端到端验收主线。
- 文件工具与命令执行可以分阶段交付，但都属于 v0.4 的验收范围。
- 影响：进程管理、取消后的状态判断与实际结果报告进入本版本设计范围。
- 执行环境的信任与隔离承诺见 Q2；可执行命令范围、审批粒度、具体进程合同和验收指标尚待决定。

### Q2：命令执行的信任前提与隔离承诺

- 用户选择：A，面向受信任的本地项目；确认日期为 2026-09-20。
- 命令在宿主机上以当前用户权限执行；本版设计审批、输出限制、超时与进程清理，不承诺操作
  系统级隔离。不可信项目的代码执行不属于本版支持范围。
- 用户明确认为 sandbox 级隔离应作为独立开发模块；本次记录这一模块边界，不为该模块分配
  版本号或冻结方案。
- 工作目录约束与审批不等于沙箱，项目受信任也不自动授予每次工具调用的执行许可。
- 术语见[v0.4 工具执行语境](../context/v0.4-tools-glossary.md)。

### Q3：平台范围

- 用户选择：A，仅 Windows；确认日期为 2026-09-20。
- 用户明确暂时不考虑 Windows 之外的平台；v0.4 不规划其他平台的命令执行实现或验收。
- 模型无关与新增工具不要求 AgentLoop 增加工具分支的目标继续有效。

### Q4：命令表达方式

- 用户选择：A，程序名与参数数组；确认日期为 2026-09-20。
- 直接启动程序，不隐式解释管道、重定向等 Shell 语法；首版不采用 Shell 字符串接口或预定义
  任务 ID 作为唯一命令表达方式。
- 此形式仍可表达解释器或脚本调用，不构成隔离措施。程序解析、工作目录、环境变量、审批展示
  和进程结果的具体合同尚待确定。

### Q5：用户可选择的工具能力范围

- 用户选择：A，提供分析、编辑、执行三档；确认日期为 2026-09-20。
- 分析包含发现、读取与搜索；编辑在此基础上增加创建、修改；执行再增加命令执行。
- 范围由用户或宿主选择，本轮固定；具体调用仍经过权限检查。选择执行范围不等于批准命令，
  已注册也不等于本轮可用。
- 默认范围由 Q15 确定为执行；具体入口、配置优先级以及与已有工具的映射尚待合同设计。

### Q6：精确编辑的首版形式

- 用户选择：A，精确文本替换；确认日期为 2026-09-20。
- 提供 `old_text` 与 `new_text`，明确匹配位置后修改；首版不增加 unified diff 编辑接口。
- 匹配歧义、修改冲突、多处修改的原子性和失败后的文件状态仍需形成明确合同。

### Q7：命令审批的有效范围

- 用户回答（2026-09-20）：“每个命令都审批，然后我们的 agent 提供当前 session 相似命令全部
  后续不需要用户再次确认审批。”
- 已确认方向：默认询问，用户可以选择本次允许，或授予当前 Session 内后续同类命令免于再次
  交互审批的允许规则。命中规则后仍需执行权限判断。
- “相似命令”的匹配范围已由 Q11 收敛为固定程序与参数前缀，具体规则字段仍待合同设计。
- 既有 Session 规则基线：授予与撤销作为事件保存、不能覆盖 DENY、不能跨 Session 传播；
  新命令规则的数据表示及与现有文件规则的兼容仍需设计。

### Q8：副作用不确定后的本轮处置

- 用户选择：A，停止本轮；确认日期为 2026-09-20。
- 自动超时或异常后，若不能确认进程清理或副作用状态，保存已知结果与不确定状态并交还用户；
  不继续模型或工具调用，不进入自动只读诊断或重试原调用。
- 用户主动取消仍结束本轮。确定失败、进程已终止与副作用状态的具体表达仍需形成结果合同。

### Q9：创建与整文件覆盖的边界

- 用户选择：A，新建与修改严格分开；确认日期为 2026-09-20。
- 创建工具遇到已有文件失败；已有文件的修改走精确编辑。原来的无保护整文件覆盖工具不向
  v0.4 模型开放，不另提供整文件替换接口。
- 旧工具历史事件的读取与旧权限规则的处置属于兼容性设计，不以删除历史事实的方式迁移。

### Q10：精确编辑的冲突前提

- 用户选择：A，整个文件版本必须一致；确认日期为 2026-09-20。
- 编辑携带读取时的文件版本标识；任何内容变化都拒绝修改，即使目标旧文本仍唯一匹配。
  发生冲突后重新读取并重新决定，不能在旧前提下直接重试写入。
- 接受的代价：无关位置的修改也会触发冲突。
- 待设计：版本标识、检查与写入之间的并发窗口、文件提交语义及其可验证保证。此取舍本身
  不证明已经解决并发写入问题。

### Q11：Session 命令规则的匹配范围

- 用户选择：B，固定程序与参数前缀，允许尾部参数变化；确认日期为 2026-09-20。
- 例如明确批准 `python -m pytest …` 后，改变测试文件或增加尾部测试参数可以复用规则。
- 按参数数组匹配，绑定实际程序、工作目录与执行环境；审批界面显示允许范围。不由模型自由
  判断“相似”，不默认扩大为所有 `python …` 命令。
- 此许可允许所批准命令范围内的可变参数，不承诺参数或项目代码没有副作用；Q2 的受信任宿主
  执行前提继续适用。

### Q12：一次精确编辑的变更单元

- 用户选择：B，一个文件、多组替换；确认日期为 2026-09-20。
- 所有旧文本基于同一读取版本检查；任一项不匹配、有歧义或彼此重叠，就不写入。
- 全部满足后一次提交该文件的全部变更；首版不做跨文件事务。
- 文件版本前提遵循 Q10，具体提交与中断保证仍需详细设计及验证。

### Q13：工具结果表示

- 用户选择：A，统一结构化结果外层，加工具专属数据；确认日期为 2026-09-20。
- 明确表达执行状态、适用的退出码、截断情况与修改结果；模型可见输出由这份规范结果生成。
- 用户同时询问 Function Calling 是否必须以“JSON 2.0”返回。官方协议核对说明：JSON 是数据
  格式；JSON-RPC 2.0 是使用 JSON 的调用协议，定义 `jsonrpc`、`id`、`result/error` 等字段。
  模型工具调用并不因此必须采用 JSON-RPC 2.0；DeepSeek 的工具示例返回普通文本 `content`。
  来源：[JSON-RPC 2.0](https://www.jsonrpc.org/specification)、
  [DeepSeek Tool Calls](https://api-docs.deepseek.com/guides/tool_calls/)，核对日期 2026-09-20。
- 设计建议：Core 使用可序列化为 JSON 的类型化结果，Provider Adapter 按模型 API 要求编码；
  不为本地 Handler 调用引入 JSON-RPC 协议。具体 Schema 和投影仍待完整合同确认。

### Q14：超量命令输出的保留方式

- 用户选择：A，有限预览加有容量上限的本地日志；确认日期为 2026-09-20。
- 给模型的输出有长度限制，其余内容进入可分段读取的日志；超过保存上限时明确报告丢失。
- 日志读取、容量控制与清理进入 v0.4 范围；不能把截断预览当作完整输出，也不依赖重跑命令
  才能查看已保留的详细结果。
- Session 归属与保留期限由 Q17 确定；具体限额与清理合同仍待设计。

### Q15：默认工具能力范围

- 用户选择：C，默认执行范围；确认日期为 2026-09-20。
- 默认开放分析、编辑与命令执行能力；用户可以主动收窄为分析或编辑范围。
- 这决定本轮工具可用性，不免除具体调用的权限判断或命令审批；Q7、Q11 继续适用。

### Q16：文件发现与搜索的默认集合

- 用户选择：A，默认面向源码；确认日期为 2026-09-20。
- 发现与搜索默认遵循 `.gitignore`，跳过 `.git` 以及常见依赖、构建产物目录；提供显式扩大
  搜索范围的选项，具体扩展范围写入工具合同。
- 搜索忽略规则不是访问权限。对已知路径的直接读取另按路径与权限合同判断，不能把搜索未
  返回某文件理解为禁止读取，也不能把扩大搜索范围理解为放宽路径边界。

### Q17：命令输出日志的保留期限

- 用户选择：A，随持久化 Session 保留；确认日期为 2026-09-20。
- 恢复同一 Session 后仍能分段读取已保存的命令输出，直到用户清理日志或删除对应 Session。
- 每份日志及全部日志的总占用均有容量上限；保留期限不等于无限保存，超限造成的未保存内容
  必须明确报告。限额耗尽时的处置与清理入口仍待合同设计。

### Q18：明确的验证失败后是否继续修复

- 用户选择：A，允许在预算内继续修复；确认日期为 2026-09-20。
- 验证命令已确定结束、结果明确时，Agent 可以依据失败结果修复并再次验证；受修复次数与
  总工具调用预算约束，每次调用仍须满足能力范围和权限检查。
- 预算数值与耗尽时的报告形式仍待设计；遇到 Q8 的副作用或清理状态不确定情形立即停止本轮，
  不以“继续修复”为理由重试。用户主动取消也结束本轮。

### Q19：命令环境的控制权

- 用户选择：A，环境由宿主配置；确认日期为 2026-09-23。
- 模型只提供程序、参数与工作目录，不提供环境变量覆盖项；Session 命令规则继续绑定实际执行
  环境。环境变化时重新判断规则是否适用，不沿用失效许可。
- 这是调用合同，不是沙箱；命令自身能做什么仍受 Q2 的宿主执行前提约束。

### Q20：首版文本搜索语法

- 用户选择：A，只支持字面文本搜索；确认日期为 2026-09-23。
- 支持限定路径、返回行号与上下文；首版不增加正则表达式选项。

### Q21：现有 v0.3 Session 的兼容范围

- 用户选择：B，并明确“不需要旧 session”；确认日期为 2026-09-23。
- v0.4 不以恢复、继续执行旧 v0.3 Session 为交付要求；升级后的工作可以从新 Session 开始。
  不建设旧记录迁移或旧权限向新工具授权的转换。此决定不授权删除原始历史数据。
- 原选项中的“只供历史查看”按保留原始记录理解，不扩大成必须开发旧格式历史查看器；若
  现有读取路径天然兼容，可保留，但不为本版增加旧记录兼容工程。
- 用户追问为何新增工具会影响 Session。核对结论：单纯增加注册项通常无需改旧 Session；
  本版另外调整结果合同与权限规则，而这些是已持久化的数据，可能涉及恢复兼容。
- 代码证据：[JSONL Session](../../src/jdagent/adapters/jsonl_session.py) 的
  `_tool_result_to_data`（第 124 行）保存 `output/status/error_code/metadata` 等字段；
  `_tool_result`（第 328 行）要求 `output` 为字符串，并按现有枚举重建；`event_from_data`
  （第 503 行）只接受 schema v2。新增可选字段未必破坏读取，但更换必需字段、枚举或事件版本
  就需要明确读写策略；不能把结果结构变化当作纯注册变化。
- 仍须保证 v0.4 自身的 Session 持久化、恢复、日志访问与允许规则有效；不承诺 v0.3 程序
  读取 v0.4 新记录。不因无需旧版恢复就静默复用不兼容的旧 schema。

### Q22：真实模型闭环的验收地位

- 用户选择：A，真实 DeepSeek 闭环必须通过；确认日期为 2026-09-23。
- 验收包含真实模型完成发现、读取搜索、精确修改、真实验证及基于结果的报告。
- 确定性测试覆盖正常与失败分支；真实 Windows 文件、进程与取消清理另有集成证据，不能用
  Fake Handler 的成功替代。Live 不替代故障注入，也不以仅生成了命令作为执行成功。

### Q23：v0.3 遗留问题对 v0.4 的阻塞范围

- 用户选择：A，按依赖划分；确认日期为 2026-09-23。
- 影响工具执行、权限、Session 或基础回归的遗留问题必须在依赖它们的 v0.4 实现前处理；
  无关的 RAG 缺口独立跟踪，不以全部 v0.3 工程收尾作为 v0.4 的统一启动前提。
- 用户补充：“我暂时没有想到 v0.4 会和 v0.3 产生破坏性回归的问题。”这记录当前预期，不
  等同于已验证没有回归。当前未发现本版实现造成的破坏，因为尚未开始实现；只识别共用的
  Context、Session、Loop 和装配路径作为后续回归范围。
- 此裁定仅调整 v0.3 → v0.4 的跨版本启动条件，不宣称 v0.3 工程验收通过，不豁免 v0.4 新
  引入的回归，也不自动批准 v0.4 整体设计或授权产品代码实现。
- 执行时固定实现前基线：保留已知 RAG 失败的准确身份和证据，区分既有失败、按本版范围
  有意变化的断言和新回归；不能整体跳过所有 RAG 或 Session 相关测试。
