## 1. 批准范围与当前门禁

项目所有者批准按本文的分阶段路线推进 v0.3。批准覆盖高层设计、ADR-0006、P1 默认项、阶段顺序、
阶段退出条件，以及在这些约束内修改代码、测试和权威文档的实现范围。

本批准不把尚未形成的详细合同视为已经批准，也不把计划中的建议文件名、类名、Commit 数量或内部
算法提升为产品合同。M0 是已批准实施计划的第一个阶段；M0 关闭并由项目所有者批准其产物前，
不得开始 M1 的实质性产品代码。之后按阶段退出条件推进，不要求每个局部实现判断都回到项目所有者。

版本状态在实现期间保持 `Approved`。只有工程验收通过时才可改为 `Implemented`；学习出口尚未
完成时必须明确记录为 `Implemented（学习出口待执行）`。

本文中的 Commit 是建议的审查边界，不构成持续的 Git `commit`、`push` 或分支操作授权。具体任务
是否执行 Git 操作仍遵循仓库的 Agent 协作规则和项目所有者当次授权。

## 2. 核心结果与约束来源

v0.3 只交付一个核心端到端结果：JDAgent 从当前 Workspace 获准使用的知识库中检索 Evidence，
在预算内把 Evidence 提供给生成模型，并返回可核验的 Citation，同时把无 Evidence 支持的内容明确
表示为 Model Supplement。

实现者按以下顺序解释约束：

1. 项目所有者的最新明确裁定；
2. 已批准需求、架构、ADR、不变量和验收标准；
3. 仓库中的代码、测试、Runtime Event、Trace 和可复现实验；
4. 本计划的阶段顺序、退出条件和建议 Commit；
5. P1 起始默认值和非规范性实现建议。

代码或测试与已批准文档冲突时，不能把任一方默认为真；先判断是实现缺陷、过时测试、文档遗漏还是
真实设计冲突，再修复唯一事实源。聊天摘要、Agent 私有记忆和计划外临时文件不参与裁定。

v0.3 的范围、不变量、所有权、失败语义、安全边界和 Eval 门禁由关联高层设计拥有。本文不复制
第二份定义，只负责安排实现顺序和阶段证据。

## 3. Cursor 的自主裁量

### 3.1 可以自行决定

Cursor 作为实现者，应主动阅读现有代码和测试并完成局部设计，不把本文当成逐文件施工脚本。在不
改变已批准产品语义的前提下，可以自行决定：

- Python 包、模块、文件、类、函数和内部类型的具体组织；
- 内部算法、数据结构、同步方式和测试夹具，只要满足已批准的不变量与性能/失败合同；
- 建议 Commit 的进一步拆分，或把两个高度耦合且无法独立通过门禁的小项合并；
- 为保持深模块、依赖方向或可测试性所需的局部重构；
- 测试文件布局、参数化方式、Fake 的内部实现和故障注入方法；
- P1 起始值在 Eval 证据支持下的调整，并同步记录基线、理由和回归影响；
- 文档未明确但不会改变外部合同、状态所有权或重大风险的局部歧义。

计划中出现的 Interface 名称描述职责，不强制等同于 Python `Protocol`、类或文件。只有行为确实在
两个 Adapter 间变化时才建立 seam；不得为了照抄计划预创建空 Port、基类、配置键或占位包。

### 3.2 发生具体冲突时的处理

实现中发现冲突或计划无法直接落地时，Cursor 应先自行完成以下判断：

1. 固定冲突证据：相关文档位置、当前代码、测试、Runtime Event、第三方行为或可复现实验；
2. 区分局部实现冲突与产品语义冲突；
3. 对局部冲突选择满足不变量、事实所有权和阶段退出条件的最小一致方案；
4. 用测试证明选择，并更新真正拥有该事实的文档，而不是增加第二份说明；
5. 在交接中报告偏离了哪项建议、为什么、验证了什么和剩余风险。

以下局部情况不要求停下等待：建议文件布局不适合现有代码、某个建议 Commit 过大或不可独立验证、
现有 Interface 可以更小、更深、第三方 SDK 需要 Adapter 内部转换、测试暴露非规范性的实现假设。

以下情况必须停止相关写入并升级给项目所有者：

- 两份已批准事实互相冲突，且没有最新裁定可以确定保留哪一份；
- 需要改变核心结果、明确非目标、架构不变量、事实所有权或公开失败语义；
- 需要把 P2、额外格式、额外 Provider、Agentic RAG、长期记忆或 Context Orchestration 纳入 v0.3；
- 需要新增未批准的运行依赖、破坏性迁移、秘密存储方式或安全信任模型；
- 需要改变 Runtime Event/Headless v2 的兼容边界，或恢复 v1 兼容范围；
- 证据不足以定义可验证行为，继续实现只能依赖猜测；
- 需要覆盖他人未提交变更、修改 Git 边界或执行未授权的 Git/破坏性操作。

## 4. Commit 与验证原则

- 每个 Commit 交付一个可观察行为或一个可独立验证的深模块增量，同时包含相应测试。
- 不按“先建所有领域类型、再建所有 Port、再建所有 Adapter”做横向空壳提交。
- 新 Interface 与首个真实 caller、生产或内存/Fake Adapter、失败测试一起落地。
- 测试通过模块的 Interface 观察行为，不绑定私有实现；内部重构不应迫使行为测试重写。
- 默认测试离线、确定性，不要求 Milvus、Embedding Provider 或 DeepSeek 凭证。
- 真实 Milvus、Embedding 和 DeepSeek 验证显式 opt-in，并且不记录 Query、Evidence、回答或秘密正文。
- 每个 Commit 至少运行相关 Pytest、Ruff format/check 和 Pyright；每个 Milestone 关闭前运行完整离线
  套件和 `git diff --check`。
- 建议 Commit 可以调整，但不得跨过 Milestone 退出条件，也不得把 Runtime v2、Milvus 生命周期和
  Citation 一次性混入不可审查的大提交。
- 阶段内可连续实现；M2、M4、M5 和 M6 关闭时固定 revision 或显式工作树快照进行相称评审。

## 6. M1：Knowledge Catalog 管理纵向切片

目标：用户可以管理 Connection、Knowledge Base 和 Workspace Binding；不摄取、不检索，也不要求
Milvus 或 Embedding 可用。

建议 Commit：

1. `feat(knowledge): add catalog bootstrap and integrity guard`
   - SQLite Schema、Migration 前备份、轻量完整性检查和损坏 fail closed；
   - 普通 Agent 启动不打开或 Ping 知识外部依赖。
2. `feat(knowledge): manage connections and knowledge bases`
   - register/test/list/remove 与 create/list/status/delete 的批准语义；
   - 稳定 ID、名称冲突和 credential reference 脱敏。
3. `feat(knowledge): manage workspace knowledge bindings`
   - bind/unbind/list、Workspace Identity 分区和无效引用分类。
4. `feat(cli): expose connection kb and binding commands`
   - CLI 只调用 Application Use Case，不直接访问 SQLite、Milvus 或文件对象。

退出条件：完全离线创建、列出和绑定知识库；重开 Catalog 后状态一致；损坏 Catalog 不影响普通
Agent；没有为尚不存在的外部 Provider 创建空 Adapter。

## 7. M2：确定性来源解析

目标：把 Raw Source Artifact 确定性转换为具有稳定 Locator 的 Parsed Source Snapshot、Parent
Segment 和 Child Chunk，不接入 Runtime。

建议 Commit：

1. `feat(ingestion): add content-addressed source store`
   - 原子持久化、Hash 校验、幂等对象写入和共享引用；
   - Source Store 只拥有不可变字节，不拥有 Source Version 生命周期。
2. `feat(ingestion): add strict decoding and txt parsing`
   - BOM、strict UTF-8、charset-normalizer 和显式 Codec；
   - 歧义、替换字符、损坏输入和文件限制失败测试。
3. `feat(ingestion): add markdown parsing and locators`
   - 标题、列表、引用、围栏代码块和表格的结构定位。
4. `feat(ingestion): add csv parsing and limits`
   - Header、多行字段、字段边界拆分、行列 Locator 和字段大小保护。
5. `feat(ingestion): add parent child chunking`
   - Parent/Child 身份、结构完整切分、选择性 Overlap 和去重所需元数据。

退出条件：固定输入产生稳定 Snapshot 与 Chunk；Raw Hash、Snapshot 身份和 Locator 往返 100%；
中文、英文、CSV、编码歧义和边界样本可离线复现；M2 固定快照完成评审。

## 8. M3：索引与来源生命周期

目标：完成独立于 Agent Runtime 的真实来源 Add/Replace/Deactivate/Reactivate/Delete、激活和恢复。

建议 Commit：

1. `feat(embedding): add openai-compatible embedding adapter`
   - Profile fingerprint、批处理、Timeout、Retry、维度、数量和有限数值校验；
   - Fake Embedding 走与生产相同的调用路径。
2. `feat(index): add milvus generation and revision adapter`
   - Generation Collection、HNSW、Dense/BM25 字段和 `mixed_zh_en_v1` Analyzer fixture；
   - Catalog 物理映射是唯一读目标，Revision Filter 在 top-K 前应用。
3. `feat(ingestion): add source add and replace saga`
   - 稳定 Operation ID、每文件 all-or-nothing、验证后激活；
   - 任一阶段失败时旧版本继续可读。
4. `feat(ingestion): add deactivate reactivate and delete`
   - Content Revision、`DELETE_PENDING`、Citation 墓碑、`DELETED` 与对象损坏区分。
5. `feat(ingestion): add mutation lease retry and reconcile`
   - TTL、Heartbeat、过期接管、幂等重试、物理清理与禁止损坏 Catalog GC。
6. `feat(cli): expose source and operation commands`
   - add/replace/deactivate/reactivate/delete/status/retry/reconcile；
   - 破坏性 Headless 操作要求显式确认。

PyMilvus 和 charset-normalizer 的精确版本、导入位置和 optional-extra 组织由实现者依据 clean-env、
启动隔离和 SDK 证据决定；基础安装不得自动引入本地模型栈，普通 Agent 不得因 RAG extra 缺失失败。

退出条件：真实或受控 Milvus 环境中完成完整来源生命周期；六个 Saga 阶段前后崩溃均可解释并
收敛；Catalog/alias 漂移、物理 Collection 缺失和混合 Revision 不会读到错误目标。

## 9. M4：Retrieval 与 Prepared Turn Knowledge

目标：通过一个小的 Turn Knowledge Preparation Interface 隐藏每库检索、Embedding Profile 分组、
跨库融合、Parent Expansion、预算与失败聚合；不修改 Agent Loop。

建议 Commit：

1. `feat(retrieval): retrieve one frozen knowledge base`
   - BM25-only、Dense-only、Hybrid+RRF；
   - 成功空结果与稳定 typed failure。
2. `feat(retrieval): group embedding profiles and fuse knowledge bases`
   - 每个完整 Profile fingerprint 每 Turn 一份 Query Vector；
   - 跨库等权排名融合、重复 Evidence 去重和分组失败隔离。
3. `feat(retrieval): expand parents and enforce evidence budget`
   - Parent Expansion、全局去重、候选/Rerank/Evidence 三层预算；
   - 形成不可变 PTK 和穷尽的 Turn Retrieval Outcome。
4. `feat(retrieval): add optional global reranker fallback`（条件项）
   - 默认关闭；先用 Fake 固定全局排序和固定回退合同；
   - 真实 Adapter 只有通过关联 Eval 门禁后才可启用。

退出条件：使用 Fake/内存 Adapter 直接调用 Preparation Interface 即可覆盖全部 Outcome、单库失败、
多 Profile、多库和预算行为；Child Retrieval 与 Final PTK Eval 分开报告；M4 固定快照完成评审。

## 10. M5：Runtime v2 与 Citation

目标：把已经稳定的 PTK 作为不可变输入接入现有 Coordinator、ContextBuilder 和 Agent Loop，一次性
完成纯 Runtime Event/Headless v2 与 Citation 所有权切换。

建议 Commit：

1. `feat(runtime): switch new sessions and headless output to schema v2`
   - 新 Session 全部使用 v2；v1 resume 明确 Unsupported；未知 Schema 不是 Corrupt Tail；
   - 无 Binding 的普通 Turn 输出 `NOT_CONFIGURED`，不需要 Milvus。
2. `feat(runtime): prepare and record turn knowledge`
   - User Message 后冻结 Binding 和读目标；首次模型调用前写 TRR；
   - ContextBuilder 接收 Runtime Events、当前 PTK 和 capabilities；
   - 同一 Turn 所有模型/工具循环复用 PTK，取消和中断显式关闭 Turn。
3. `feat(citation): validate turn-scoped evidence references`
   - 拒绝未知、跨 Turn、被预算裁剪和原文伪造的 Reference；
   - 最多一次 Repair，不重新检索、不扩大 Evidence、不执行 Tool。
4. `feat(citation): persist and present verified citations`
   - `assistant_message_completed` 独占结构化 Citation；
   - Citation Resolver 区分可打开、墓碑和损坏来源；
   - Headless v2、Trace 与 Presenter 使用同一规范事实。

退出条件：Fake 全链路覆盖 Prompt → PTK → Model → Citation → Session v2；Citation 时序和终止
事件 100% 符合合同；普通无 RAG 对话、Tool Call、取消和恢复回归通过；M5 固定快照完成评审。

## 11. M6：Eval、安装、验收与关闭

目标：以实现前基线、实现后 Eval、故障实验、安装证据和独立评审关闭工程范围，不用聚合分数掩盖
失败样本。

建议 Commit：

1. `test(eval): enforce retrieval and final ptk gates`
   - Parser/Locator、Child Retrieval、Final PTK 分层执行；
   - 输出总体与中文、英文、CSV、多库切片，保存失败样本。
2. `test(eval): enforce answer and citation gates`
   - DeepSeek 每题按批准协议独立运行至少三次；
   - 保存逐次结果、聚合结果、配置指纹和 Usage，不挑选最佳一次。
3. `test(integration): verify live rag and recovery failures`
   - Milvus、Embedding、Analyzer、Revision、Saga、Repair 和依赖不可用矩阵。
4. `build(v0.3): verify optional rag installation and lazy composition`
   - 基础与 RAG extra 的 clean-env wheel 验证；
   - console script、`python -m jdagent`、无 Binding 和有 Binding 启动路径。
5. `docs(v0.3): record verification review and remaining risks`
   - 固定评审 revision，完成独立 Standards/Spec 评审并处置 finding；
   - 更新 README、当前状态、索引、评审证据和学习记录。

退出条件：Ruff format/check、Pyright strict、完整离线测试、显式 Live/集成测试、安装验证和文档链接
通过；需求到测试/证据可追踪；无未处置 Blocker/High；项目所有者裁定工程验收状态。

## 12. 横向测试矩阵

| 观察面 | 默认门禁 | Live/人工补充 |
| --- | --- | --- |
| Catalog/Store | SQLite 临时目录、内存/Fake Store、损坏与迁移夹具 | 备份恢复与权限环境 |
| Parser/Locator | 固定 Corpus、编码与格式边界、100% 往返 | 人工检查 Gold Locator |
| Index | 注入式 Adapter 测试、Revision Filter 合同 | Milvus Standalone、Analyzer/HNSW |
| Ingestion | Fake Clock、稳定 Operation ID、逐阶段故障注入 | 进程退出与 Reconcile |
| Retrieval/PTK | Fake Embedding/Index/Reranker、固定排名 | 真实 Embedding + Milvus Eval |
| Runtime/Citation | Fake Model、规范事件顺序、非法 Reference | DeepSeek Answer/Citation Eval |
| Packaging | 基础安装与缺少 RAG extra | RAG extra clean-env 安装 |

每个阶段都必须覆盖正常、空、错、重复、取消或中断，以及副作用未发生的断言。故障无法在自动测试中
稳定制造时，先建立确定性 seam 或进程夹具，不使用随机 sleep 证明正确性。

## 13. 明确延后

以下内容不因实现便利进入 v0.3：

- Query Rewrite、LLM Router、Agentic RAG 和检索 Tool；
- JSON、PDF、HTML、Excel、代码专用 Parser、网页采集和文件监控；
- MCP/外部 Knowledge Provider 空壳、本地模型管理和多 Reranker；
- Milvus Distributed、多用户、高并发、后台队列和可视化 Dashboard；
- 长期记忆、通用 Context Orchestration、Compaction 和多模态 Evidence；
- 为 v1 Session/Headless 保留双写、迁移或长期兼容层。

若真实失败证据要求其中一项，先按高层设计的复审条件更新需求、设计、Eval 与范围，并由项目所有者
批准；不得在实现 Commit 中顺手加入。

## 14. Cursor 阶段交接格式

每个建议 Commit 或等价增量完成后，Cursor 至少报告：

```yaml
increment: <milestone and behavior>
requirements:
  - <requirement or invariant>
changes:
  - <files or modules and why>
decisions:
  - <local implementation judgment or deviation from this plan>
verification:
  - <command and result>
unverified:
  - <check not run and why>
remaining_risks:
  - <risk or none>
next_increment: <smallest safe next behavior>
```

计划的价值是提供顺序、退出条件和审查范围，而不是替实现者思考。Cursor 应对自己的局部设计、
Diff、测试和证据负责；“按计划写了代码”本身不构成完成证据。
