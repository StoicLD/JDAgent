## 1. 优先级含义

- **P1**：不改变关联高层设计的已批准边界；必须在对应实现 Milestone 关闭前固化、测试或由 Eval
  调整。
- **P2**：不阻塞 v0.3 核心端到端结果；只有时间、证据或真实需求允许时才进入后续增量。

P1 中的数字是起始默认值，不是假装已经获得基准证据。Eval 可以调整，但必须记录基线、变化理由和
回归影响。

## 2. P1：实施前使用的默认方案

### P1.1 三层检索预算

起始默认值：

- 每 Knowledge Base：Dense top 20、BM25 top 20，库内 RRF 后保留 20 个 Child；
- 跨库融合后：最多 40 个 Child 进入可选 Reranker；
- 最终 Evidence：最多 6,000 tokens、8 个 Parent、单 Parent 最多 2,000 tokens。

预算应用顺序固定为候选生成、库内融合、跨库融合、可选 Rerank、Parent Expansion、最终 Token
裁剪。不得先注入 Parent 再依赖模型 Context Limit 被动截断。

Eval 应按单库、多库、中文、英文、CSV 和长 Parent 切片分别报告 Recall 与预算损失。

### P1.2 跨库融合

- 默认所有 Knowledge Base 等权；
- 使用排名做跨库 RRF，不比较原始 Dense/BM25 分数；
- 同一 Source Version/Locator 的重复 Evidence 在全局阶段去重；
- 不提供 per-Binding 权重；
- 启用 Reranker 时只精排全局候选一次；
- 某库没有命中不算失败，仍记录成功空结果。

### P1.3 Embedding Adapter

- 使用独立 OpenAI-compatible `/embeddings` HTTP Adapter；
- Base URL、Model ID、Dimension、Normalization、Timeout 和 Batch Size 显式配置；
- 文档与 Query 必须使用同一 Embedding Profile；
- Effective Knowledge Bases 按完整 Embedding Profile fingerprint 分组；相同 Profile 每 Turn 只生成
  一份 Query Vector，不同模型、维度或归一化合同绝不复用；
- 某个 Profile 的 Query Embedding 失败只影响该组知识库，并参与 Turn Retrieval Outcome 计算；
- 默认请求超时 30 秒，最多重试 2 次可重试网络/限流错误；
- 默认 Batch Size 由 Provider Profile 指定，未指定时从 32 起步并由集成测试调整；
- 返回向量数量、维度和有限数值必须完整验证；
- 不把 DeepSeek 生成模型配置隐式复用成 Embedding 配置；
- 自动测试使用 Fake Embedding，真实集成测试需要显式 opt-in。

### P1.4 Cross-Encoder

- 默认关闭且不进入基础安装依赖；
- RerankerPort 先使用 Fake 验证排序合同；
- 只有真实 Adapter、固定模型身份、超时/错误映射和架构 §17.4 Eval 门禁同时通过才可启用；
- 实现和故障测试必须符合架构 §5/§11 的全局 Reranker seam 与固定回退语义，本附页不复制第二份
  失败合同；
- 一次 Turn 最多调用一次 Reranker。

### P1.5 `mixed_zh_en_v1`

- 以 Milvus Chinese/Jieba 能力和保留 Latin/数字 Token 的 Filter 组合为起点；
- Index 与 Query 使用相同 Analyzer 配置；
- 使用 `run_analyzer` 固定中文词、英文标识符、数字、Markdown 标题和 CSV 值的 Token Fixture；
- 领域词典为空是默认状态；
- 词典变更产生新 Retrieval Language Profile 版本和新 Index Generation；
- 若任一语言切片未过门禁，Profile 不能仅因名称为“mixed”而被接受。

### P1.6 文件与批次保护

起始默认值：

- 单个 Raw Source Artifact 上限 50 MiB；
- 单次批次最多 100 个文件；
- 不设置独立行数上限，CSV 受文件大小、字段大小和解析预算限制；
- 单 CSV 字段上限 10 MiB，超过时该文件失败，不截断；
- 文件在进入 Parser 前固定原始字节哈希；
- 解析和 Chunk 数量设置可配置保护阈值，并返回逐文件错误；
- 用户显式提高限制时仍不得绕过磁盘空间检查。

这些限制属于本地单用户防护，不宣称为多租户配额。

### P1.7 编码判定

- 显式 Codec 优先；
- 自动顺序为 BOM、strict UTF-8、charset-normalizer；
- 无候选、候选歧义、解码错误或出现替换字符均使该文件失败；
- Error 显示候选名称和置信信息，但不输出 Source 正文；
- CLI 提供显式 `--encoding` 重试；
- Gold Corpus 包含 UTF-8、UTF-8 BOM、UTF-16、GB18030 和歧义/损坏样本。

### P1.8 Knowledge Mutation Lease

起始默认值：

- Lease TTL 5 分钟；
- Heartbeat 每 30 秒；
- 同一 Operation ID 重试时恢复原 Saga，而不是新建重复 Source Version；
- 未过期 Lease 返回 `KNOWLEDGE_BUSY`，不排队；
- Lease 过期后只能由 Reconciler 或显式 retry 接管；
- Activation 使用短 Catalog 事务；
- Retrieval 不获取 Mutation Lease。

故障测试必须覆盖进程在 Raw Store、Parse、Embedding、Milvus Write、Validation 和 Activation 前后
分别退出。

### P1.9 Backup、Integrity 与 GC

- Schema Migration 前必须创建 SQLite Online Backup 并执行完整性校验；
- Catalog 发生变化时默认每日备份一次，保留最近 7 份；
- 启动使用轻量检查，完整 `integrity_check` 和对象 Hash Scrub 由维护命令执行；
- 配置替换后的旧 Index Generation 默认保留 7 天再回收；
- Source Delete 不受普通保留期保护；墓碑起点与终态遵循架构 §7.5，本节只固定物理 GC 默认值；
- 共享内容寻址对象只有在 Catalog 证明没有其他 Source Version 引用后才可 GC；对象意外缺失报告
  来源损坏，不转换成删除状态；
- 自动 GC 只删除 Catalog 明确证明不可达且已超过保留期的对象；
- Catalog 损坏时禁止 GC。

### P1.10 Runtime Read Target 验证

Catalog、物理 Collection、alias 与 Revision Filter 的唯一读路径由架构 §8 定义。实现 Milestone
必须通过以下故障测试，不在本附页重新定义 winner：

- Catalog 与 alias 指向不同 Generation；
- Catalog 记录的物理 Collection 缺失；
- Dense 与 BM25/Sparse 查询混有多个 Revision；
- Reconciler 在 alias 切换前后崩溃。

### P1.11 CLI 形状

默认命令树：

```text
jdagent knowledge connection add|test|list|remove
jdagent knowledge kb create|list|status|delete
jdagent knowledge source add|replace|deactivate|reactivate|delete
jdagent knowledge binding add|remove|list
jdagent knowledge operation status|retry|reconcile
```

CLI token 只是一层 Adapter 映射：`connection add` 调用 Connection `register` Use Case，
`binding add/remove` 分别调用 `bind/unbind`。Application 语义以架构为准，CLI 精确 token 只在本节
维护，避免两处命令合同漂移。

- 所有变更命令调用 Application Use Case，不直接操作 SQLite 或 Milvus；
- 输出稳定 ID；名称冲突时失败，不做模糊选择；
- Delete/remove 要求确认，Headless 必须显式 `--yes`；
- CLI 命令不可注册到 Tool Registry；
- Interactive `/knowledge status`、`/knowledge sources` 和 `/knowledge bindings` 是 P1 便利入口，
  复用同一 Use Case；破坏性 slash command 默认不提供。

### P1.12 Runtime Event/Headless v2 细节

- 新 Session 只写 v2，v1 Session 不 resume；
- 提供显式旧 Session 清理命令或迁移说明，不在启动时自动删除；
- Runtime Event/Payload v2 详细合同必须逐项实现架构 §10、§13–§14 的时序、所有权、终止和恢复
  语义；该合同获批前不得实现知识 Turn 事件；
- Headless v2 输出 `knowledge.outcome`、`knowledge.bases[]`、`citations[]` 和
  `model_supplement`；
- 未知 Schema 是 Unsupported，不是 Corrupt Tail；
- v1/v2 兼容代码不作为 v0.3 测试要求。

### P1.13 Trace 与脱敏

默认记录：

- Operation/Turn/Knowledge Base/Generation/Revision ID；
- 各阶段耗时和候选计数；
- 预算、模式、配置指纹和稳定错误原因；
- Lease/Reconcile/Citation Repair 状态。

默认不记录：

- Query、Evidence、Source、CSV 单元格和模型回答正文；
- Endpoint Query String、API Key、Credential Ref 的解析值；
- Milvus/HTTP 异常中未经清洗的请求数据。

### P1.14 Eval 执行

- 先记录当前无 RAG 的基线：知识问题只能由 DeepSeek 参数知识回答且没有 Citation；
- Parser/Locator 与 Child Retrieval Eval 可离线运行；
- 单独计算 Parent Expansion、去重和最终预算后的 Final PTK Gold Support Coverage；多证据题报告
  全部必需证据保留率；
- Answer/Citation Eval 默认使用现有 DeepSeek 配置并显式 opt-in Live；
- Contextual Retrieval 或 Query Rewrite 实验若被显式启用，也默认使用同一 DeepSeek 测试模型并
  分别记录 Usage；
- 每次 Eval 保存 Dataset Revision、Embedding Profile、Retrieval Profile、DeepSeek Model、Prompt
  Revision、temperature/其他 settings 和运行时间；
- DeepSeek Answer/Citation Eval 每题默认独立运行 3 次，同时保留逐次结果和聚合结果；正式 Eval
  规格在实现前固定中位数/失败判定，禁止挑选最佳一次作为发布证据；
- Answer/Citation 标注明确 answerable/unanswerable、允许的 Source Version/Locator、需要引用的
  主张和 claim–evidence 支持关系；
- Cross-Encoder、Contextual Retrieval 和 Overlap 策略分别出消融报告；
- 门禁失败必须保留失败样本，不只输出聚合分数。

### P1.15 依赖与安装

- PyMilvus 和 charset-normalizer 是 v0.3 RAG 的真实依赖候选；
- 是否放入基础依赖或 `rag` optional extra 在实施计划的安装 Milestone 通过 wheel/clean-env 测试
  决定，默认优先 optional extra，保持普通 Agent 轻量启动；
- 基础安装不得拉取 PyTorch/Transformers；
- Milvus Standalone 的启动、健康检查和版本兼容通过外部部署说明管理，不在 JDAgent 启动时自动
  拉起容器；
- Composition Root 只有实际执行知识用例或 Turn 存在 Binding 时才连接知识依赖。

## 3. P2：不阻塞 v0.3 核心结果

### P2.1 检索增强

- Query Rewrite；
- LLM/Classifier Knowledge Routing；
- Agentic RAG、多步检索和检索 Tool；
- per-Binding 权重；
- Turn-scoped Knowledge Base override；
- 动态预算和基于成本的知识库裁剪；
- 多 Reranker 或在线 Grounding Judge。

默认：全部关闭，不预创建空 Port 或配置键。

### P2.2 更多格式与来源

- JSON、PDF、HTML、Excel；
- Python/Java 等专用代码 Parser；
- 网页抓取、远程同步和文件监控；
- 图片、音频和多模态 Evidence。

默认：保留 Source/Parser seam，但不注册占位实现。

### P2.3 Provider 与部署

- MCP/外部 Knowledge Provider；
- 本地 Embedding 推理运行时与模型管理；
- OS Keyring/Secret Service；
- Milvus Distributed、高可用与远程多租户；
- per-Knowledge-Base Lease 和并行摄取；
- 分布式 Reconciler。

默认：等待真实第二实现或真实扩展需求证明 seam。

### P2.4 Eval 扩展

- MIRACL、BEIR 或其他公开检索数据集的适用切片调研；
- 更大真实企业语料；
- LLM-as-Judge 与人工双盲标注一致性；
- 成本、延迟、并发和长期漂移 Dashboard；
- 多生成模型对比。

默认：项目 Gold Corpus 和 DeepSeek 端到端测试仍是 v0.3 规范基线；公开数据不替代来源生命周期与
Citation 场景。

### P2.5 运维体验

- 可视化 Knowledge Dashboard；
- 备份导出/导入与跨设备迁移；
- 后台摄取队列和进度 UI；
- Storage Quota、容量预测与压缩；
- 自动词典建议和 Analyzer 调优界面。

默认：v0.3 使用 CLI、结构化状态和 Trace 完成可观察性闭环。

## 4. 升级规则

P2 项只有在出现以下证据时才进入正式设计：

- v0.3 Eval 或真实使用出现可复现失败；
- 已有 Interface 无法承载真实第二实现；
- 当前默认形成明确成本、正确性或运维瓶颈；
- 用户重新批准范围和相应学习目标。

不得因为某个库支持某项功能，就提前把 P2 变成依赖、配置、Port 或空壳模块。
