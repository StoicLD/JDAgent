## 主数据流和事实所有权

由学习者闭卷重建以下链路，并在实现后用真实 Trace 核对：

1. 用户输入 → Journal → 请求构造与费用预留 → LangChain 模型 → 完整响应 → 图条件分支。
2. assistant 工具列表落盘 → 顺序审批与执行 → 结果落盘 → 新请求；中途发现目录规则时如何处理。
3. 上下文超过阈值 → 摘要生成与校验 → 检查点提交 → 下一请求；失败为什么不改变原始历史。
4. 命令已启动但结果尚未保存时崩溃 → SessionRecovery → unknown 隔离；为什么不能简单重跑节点。
5. 用户显式记忆意图／后台提取 → 版本与来源检查 → 提交；为什么框架 Store 不能自动替代这些规则。

- [ ] 每条链都能说明持久化先后、权限、费用和停止条件。
- [ ] 能区分 UI 文本增量、模型候选、已保存 assistant 和用户任务真正完成。

## 故障实验

每项先由学习者写预测、依据和置信度，再运行获授权的实验；不能先看结果再补写预测。

| 故障 | 需要解释的事实 |
| --- | --- |
| 工具参数分片后断流 | 为什么不能执行；保存哪些错误和费用；怎样观察未发生副作用 |
| Usage 在完成原因之后单独到达 | 如何避免漏记和重复计数 |
| 文件修改已发生、节点尚未返回时崩溃 | Journal、工具效果和图位置为什么可能不一致；如何恢复 |
| 连续取消命令或磁盘事务 | 谁等待清理，何时释放 Session 锁，何时可以报告取消 |
| 图步数耗尽而业务调用预算尚有余量 | 如何区分拓扑配置问题和真实调用限额 |
| 记忆来源过期或后台租约被接管 | 为什么旧 worker 不能发布，停用内容为何不能复活 |
| 框架参数导致额外模型重试 | 如何通过 HTTP 次数、request_id 和费用账本发现 |
| 切到新 Adapter 后实验总额度已用完 | 为什么两种 Adapter 都必须在发送前被阻断，产品每会话预算为何不能代替实验总额度 |
| 两轮之间重载模型，旧维护请求还在等待发送 | 新旧请求分别使用哪份模型设置，归档与实际传输如何核对 |
| 后续响应重用已发起或因目录规则跳过的调用 ID | 两种情况的旧行为为何不同，下一 Turn 的初始化又如何处理 |

- [ ] 根据事件、日志和实际效果解释预测偏差，区分可以重试与必须停止的情况。
