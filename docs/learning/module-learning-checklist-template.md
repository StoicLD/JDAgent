# 模块学习检查表模板

状态：`Approved`

批准日期：2026-08-24

用途：每个实质性模块完成设计时复制本模板，创建模块专属学习清单。复制后必须把占位内容替换为
该模块的具体 Interface、数据流、失败模式和实验；通用模板本身不能作为学习出口。

执行纪律：带“学习者”的项目必须由学习者本人闭卷完成。AI 可以主持、追问、执行已授权实验和
依据证据核对，但不得代答、代填或把提示后的答案记录为首次闭卷结果。

## A. 实现前初始模型

在阅读 AI 完整推荐方案前，由学习者完成：

- [ ] 用自己的话说明问题、用户可观察结果和非目标。
- [ ] 画出当前系统的数据流和状态所有者。
- [ ] 提出至少两个实质不同的候选方案。
- [ ] 预测每个方案的主要 Trade-off 与三个失败模式。
- [ ] 写出预期验收标准和最小 Eval。
- [ ] 诚实记录未知项，没有在 AI 纠正后反向补写初始答案。

完成标准：

- [ ] 能区分学习模块、产品能力和代码模块。

## D. 方案比较与工程判断

对最终方案和至少一个被拒绝方案回答：

- [ ] 各自解决什么问题，成立需要哪些条件？
- [ ] 正确性、可靠性、安全性、延迟、成本和可维护性如何取舍？
- [ ] 为什么没有采用更简单或更流行的做法？
- [ ] 什么需求变化会推翻当前决策？
- [ ] 主流框架隐藏了什么复杂度，何时不应使用它？
- [ ] 能区分已验证事实、推断、价值判断和仍未验证的假设。

## E. 实现阅读与需求追踪

- [ ] 将每条验收标准映射到代码入口、测试和运行证据。
- [ ] 解释关键调用链，不要求背诵函数名或逐行实现。
- [ ] 指出 AI 实际实现、明确未实现和超出原设计的内容。
- [ ] 检查 Interface 是否因测试或框架类型而泄漏内部复杂度。
- [ ] 找出至少一个曾被自己或 AI 忽略、后来通过证据修正的问题。

## F. 故障实验

模块设计完成时将以下占位替换为具体、可复现的故障：

1. `<依赖失败>`
2. `<边界或预算耗尽>`
3. `<数据损坏、冲突或过期>`
4. `<取消、超时或部分副作用>`
5. `<安全、权限或不可信输入>`

对每个实验：

- [ ] 实验前写出预测、依据和置信度。

- [ ] 解释预测与结果的差异，并更新心智模型。
- [ ] 区分可以重试、必须降级、需要人工决定和必须 fail closed 的情况。

## I. 闭卷答辩

学习者应在无源码和无 AI 提示时回答：

- [ ] 模块解决什么问题，不解决什么？
- [ ] 主数据流、状态所有者和停止条件是什么？
- [ ] 为什么选择当前 Interface 和 seam？
- [ ] 三个主要失败如何发生、传播和恢复？
- [ ] 最终方案相对替代方案牺牲了什么？
- [ ] 如果规模、数据、Provider 或安全假设改变，哪里需要重构？
- [ ] 遇到一个未见过的变体时，能先形成假设和验证计划，而不是立即要求 AI 给答案。
