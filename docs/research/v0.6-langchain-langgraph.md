## 可确认的框架边界

| 机制 | 官方资料确认的行为 | 对 JDAgent 的设计含义 |
| --- | --- | --- |
| LangChain 模型接口 | Provider 集成包提供统一模型调用与消息接口；`ChatDeepSeek` 位于 `langchain-deepseek`。[模型](https://docs.langchain.com/oss/python/langchain/models)、[DeepSeek](https://docs.langchain.com/oss/python/integrations/chat/deepseek) | 可以在既有 `ModelPort` 后面引入适配器，替代手写 Provider 协议处理；领域事件仍需转换与校验。 |
| `create_agent` | 创建调用模型和工具的循环，返回 `CompiledStateGraph`；middleware 在这个图内运行。[API](https://reference.langchain.com/python/langchain/agents/create_agent)、[middleware](https://docs.langchain.com/oss/python/langchain/middleware/overview) | 它已经拥有循环、消息状态和工具调度。采用它需要逐项迁移现有行为，不能只包一层同时保留第二个主循环。 |
| `StateGraph` | 通过 state、node、edge 定义执行；node 可以是普通函数，编译时可选择 checkpointer。[Graph API](https://docs.langchain.com/oss/python/langgraph/graph-api) | 可以只替换主流程调度，node 调用既有 Context、Model、Tool 和 Journal 服务。使用图不要求同时迁移持久化。 |
| `ToolNode` | 提供工具执行、并行调度、错误处理与状态注入。[API](https://reference.langchain.com/python/langgraph.prebuilt/tool_node/ToolNode) | 直接采用会改变当前批次逐个执行的合同。保留自定义顺序执行 node 更容易维持权限、目录规则和取消语义。 |
| Checkpointer 与 Store | 前者保存 thread 内图状态，后者保存跨 thread 的应用数据；内存 saver 不跨进程保存。[Persistence](https://docs.langchain.com/oss/python/langgraph/persistence) | 两者都不能自动替代 Session 原始事实、版本化 Memory、宿主用户意图及费用账本。 |
| `interrupt` | 需要 checkpointer 和 `thread_id`；以 `Command(resume=...)` 恢复，所在 node 从函数开头重新执行。[Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts) | 当前同步等待审批可以保留。未来采用持久审批时，审批前不能先执行不可安全重复的工具。 |

表格右栏是本项目适配判断，不是框架提供的保证。LangGraph 的价值可以先体现在显式流程与分支，
不必在同一版本引入其全部持久化、人工中断和多 Agent 机制。

## 模型适配必须保持的合同

LangChain 的 `HumanMessage`、`SystemMessage`、`AIMessage` 和 `ToolMessage` 分别表示输入、
系统材料、模型响应和工具结果；工具结果通过 `tool_call_id` 配对。流式结果是可以合并的
`AIMessageChunk`，`usage_metadata` 提供可用的 token 统计，`response_metadata` 保存响应元数据。
这些机制有助于转换，但不替 JDAgent 判断一轮是否完整成功。
[消息文档](https://docs.langchain.com/oss/python/langchain/messages)

建议在 `LangChainModelPort` 的边界验证以下项目，只有证据完整后才发出 `ResponseCompleted`：

- 先合并完整工具参数，再生成 `ToolCallCompleted`；检查重复或缺失 ID、无效 JSON、
  `invalid_tool_calls` 以及工具调用与结束原因不匹配。中间 chunk 的暂时无效参数不能提前判定失败。
- `finish_reason` 不是跨所有 Provider 恒定同名的字段。DeepSeek 的映射应按锁定适配器实测；
  流自然结束不能直接等同于 `stop`，缺少结束证据仍按协议错误处理。
- Usage 可能只出现在最后的独立 chunk。不能收到 `finish_reason` 就结束迭代而漏掉费用；
  也不能把累计 usage 当成每个 chunk 的增量重复结算。
- Provider 异常需要映射为既有认证、权限、限流、连接、超时、协议等类别。取消继续传播，
  不可被通用异常分支包装成可重试模型错误。
- 显式关闭模型客户端的自动重试，或将每次底层尝试纳入现有持久账本；图重试、SDK 重试与
  结构化输出重试不能在账本之外叠加。默认重试值不应从另一个 Provider 类推。

`AIMessage` 公开了无效工具调用与用量类型，OpenAI 兼容适配器文档展示了结束原因与流式 chunk；
这些是字段机制依据，并不证明 DeepSeek 当前配置的全部边界行为。
[消息 API](https://reference.langchain.com/python/langchain/messages)、
[ChatOpenAI API](https://reference.langchain.com/python/integrations/langchain_openai/ChatOpenAI)

## 持久执行的实际边界

Checkpointer 按 `thread_id` 组织图状态，在 super-step 边界保存完整 checkpoint，也保存成功节点的
pending writes。`durability="sync"` 在下一步前写入，`async` 边执行下一步边写入，`exit` 在运行退出时写入；
后两者不能提供相同的进程崩溃恢复范围。当前 `durable-execution` 地址重定向到 Persistence，
详细模式在 [Checkpointers](https://docs.langchain.com/oss/python/langgraph/checkpointers)。

这些机制保存的是执行状态，不是外部副作用的事务。恢复可能重跑节点；已经发出命令但未保存结果的
窗口依然存在。`@task` 可以复用已经持久化的完成结果，未完成的 task 仍可能重跑，仍需要幂等键、
结果核对或标记未知副作用。不能把 durable execution 写成外部操作的 exactly-once 保证。
[Graph API](https://docs.langchain.com/oss/python/langgraph/graph-api)、
[Functional API 源码文档](https://github.com/langchain-ai/docs/blob/main/src/oss/langgraph/functional-api.mdx)

未来若同时使用 Journal 和图 checkpoint，必须先设计两者的提交顺序、关联序号、缺失时的恢复规则和
权限重新获取；仅设置相同 `session_id/thread_id` 不会解决两个存储之间的原子性。首版不启用
checkpointer 时，现有 Session 恢复继续负责崩溃处理；不能宣传已经获得图的持久恢复能力。

## 子图和状态

父子图共享 state key 时，可把编译后的子图直接作为 node；schema 不同则用包装函数显式转换。
子图 `checkpointer=None` 默认每次调用新建内部状态，并在父图有 checkpointer 时继承其持久执行能力；
`True` 跨同一 thread 的调用保留状态，`False` 不启用 checkpoint 和 interrupt。
[Subgraphs](https://docs.langchain.com/oss/python/langgraph/use-subgraphs)

JDAgent 的压缩、记忆整理和检索已有服务与独立状态所有者；只有需要独立图流程或复用明确子流程时，
才值得拆成子图。把每个函数包装为子图会增加状态转换和恢复规则，而不自动改善行为。
图 state 宜存放流程控制值及领域记录引用，避免再维护一份无限增长的完整历史。没有 checkpointer 的
首版更应通过既有 ContextService 从 Journal 构造消息，而不是让 `MessagesState` 接管全部事实。

## 依赖与验证范围

v1 文档推荐 `langchain.agents.create_agent`，旧 `LLMChain`、`ConversationChain` 等已移至
`langchain-classic`；不应以旧教程决定新设计。`langchain.messages/tools` 中部分接口本来就重导出自
`langchain-core`，因此使用 `langchain-core`、`langchain-deepseek` 和 `langgraph` 是实际使用这些框架
的组成部分，不必为安装顶层 `langchain` 而引入不使用的 Agent 工厂。
[v1 migration](https://docs.langchain.com/oss/python/migrate/langchain-v1)

实施阶段应在项目 Python 3.11 环境解析相容的稳定版本，把准确版本写入 `uv.lock`；检查 Provider 包的
传递依赖，避免将框架与 Provider 的版本号误设成必须相同。不要在设计期宣称“最新版本”已经验证。
最小验收应覆盖：离线流协议、最终请求 body、模型和工具次数、压缩及引用修复、取消和资源释放、
JSON 解析失败、Usage 缺失、断流、重启后未知副作用不重放，以及带明确调用预算的真实 DeepSeek 对照。
这些是建议验收项目，本次仅核对文档与源码，未安装新依赖或调用真实模型。
