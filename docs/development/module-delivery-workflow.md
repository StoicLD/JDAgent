# 模块交付与学习工作流

状态：`Approved`

批准日期：2026-08-24

## 目的

JDAgent 同时服务于可工作的 Agent 产品、Agent 工程实践和学习者的求职能力建设。后续版本不得只按
功能清单推进；每个模块都必须同时交付产品能力、工程证据、设计判断和可验证的学习结果。

本工作流适用于 v0.2 之后所有实质性模块。具体版本仍需单独批准需求、架构、实施计划和学习清单；
本文件不替代这些版本文档。

## 三种模块不得混同

- **学习模块**：需要系统掌握的问题域，例如 RAG、长期记忆或 Context Engineering。
- **产品能力**：用户或 Runtime 获得的端到端可观察结果。
- **代码模块**：具有一个 Interface 和一个 Implementation 的工程结构，可以是函数、类、包或跨层
  纵向切片。

一个学习模块可以横跨多个代码模块；一个代码模块也可以服务多个学习模块。不得因为学习目录中有
一个主题，就预先创建同名包、Port、基类或空壳代码。

代码模块遵循深模块原则：用尽量小的 Interface 隐藏复杂 Implementation。Interface 包含调用方必须
知道的类型、约束、不变量、顺序、错误模式、配置和性能特征。seam 只放在行为真实变化的位置；一个
Adapter 通常只证明假设中的 seam，生产与测试或两个真实实现才证明变化点存在。

## 角色与责任

### 学习者兼项目所有者

学习者不需要手工编写全部实现代码；AI 可以承担主要编码工作。但以下认知和决策责任不得外包：

1. 在查看 AI 完整方案前，写出问题、目标、非目标、当前解释和未知项。
2. 提出至少两个有实质差异的候选方案，比较适用条件、Trade-off 和失败模式。
3. 决定需求、范围、Interface、状态所有权、验收标准和接受的风险。
4. 在实现前预测关键实验和故障场景的结果。
5. 实现后阅读 Diff、关键调用链、Runtime Event、Trace 和测试证据，确认 AI 实际实现与未实现的
   内容。
6. 对失败形成自己的假设，依据证据诊断，再要求 AI 修改。
7. 闭卷解释模块、替代方案和限制，并完成延迟复测。
8. 批准需求、架构、ADR、计划和重大范围变化。

### AI

AI 可以同时承担资深指导者、实现者、批判者和模拟面试官，但不得被视为真理来源或项目批准者。
AI 负责：

- 导航主流方案、权威资料、参考实现和常见失败；
- 在学习者形成初始模型后，指出遗漏、反例和相反解释；
- 提出不同 Interface 与 seam 设计供比较；
- 按已批准设计实现代码、测试和文档；
- 生成可复现的正常、边界和故障场景；
- 报告实际运行证据、未验证部分和剩余风险；
- 通过连续追问、陌生变体和反向解释检验理解。

AI 不得：

- 在学习者尚未形成初始判断时，把一个完整推荐方案当作唯一答案灌输；
- 用自己的解释代替来源、测试、Trace 或实验；
- 代替学习者完成闭卷题、填写人工完成记录或批准提案；
- 把“代码已生成”解释为“模块已学习”或“版本已完成”；
- 为未来假设创建未经需求证明的框架、Port 或空壳模块。

## 证据纪律

判断依据按问题选择并交叉验证：

1. 已批准需求、架构、ADR 和项目事实确定本项目约束。
2. 官方文档、标准、论文和固定 revision 的参考实现说明外部机制。
3. 代码、测试、Runtime Event、Trace、日志和可复现实验说明实际行为。
4. AI 解释只作为待验证的专家假设，不单独证明正确性。

资料冲突时必须记录来源、适用条件和裁定理由；不得以“主流都是这样”结束分析。

## 每个模块的固定推进顺序

### 1. 学习者初始模型

在 AI 给出完整方案前，学习者至少记录：

- 要解决的问题和用户可观察结果；
- 当前系统为何做不到；
- 非目标与边界；
- 初步数据流和状态所有者；
- 两个候选方向；
- 三个可能失败点；
- 当前未知项。

初始模型允许不正确；它用于暴露认知变化，不能在 AI 纠正后反向补写成“原本就知道”。

### 2. 调研与方案比较

AI 补充权威来源、主流做法、反例和候选方案。学习者更新比较，至少覆盖：

- 适用条件与不适用条件；
- 正确性、可靠性、安全性、延迟、成本和可维护性；
- 数据丢失、损坏、冲突、重试和取消；
- 测试与观察方式；
- 对现有 Interface、Runtime Event 和状态所有权的影响；
- 被拒绝方案和复审条件。

### 3. 可批准的模块设计包

开始实质性实现前必须形成：

1. 需求、非目标和可验证验收标准；
2. 学习目标、必备概念和当前能力基线；
3. 候选方案比较与最终决策；
4. 模块 Interface、seam、Adapter、依赖方向和状态所有权；
5. 正常数据流、失败模型、安全与隐私约束；
6. 最小 Eval：固定场景、无新能力基线、指标、失败分类和回归门禁；
7. 分阶段实施计划与每阶段退出条件；
8. 从模板实例化的模块专属学习清单；
9. 会长期约束后续实现时所需的 ADR。

模块专属学习清单必须包含具体机制、数据流和故障问题。仅复制通用模板而不填充内容，不算完成
设计。

### 4. AI 实现与学习者控制

AI 按批准设计实现并提供需求到代码与测试的追踪。学习者至少检查：

- Diff 是否与批准范围一致；
- Interface 是否隐藏 Implementation 复杂度；
- 是否出现第二事实源或状态所有权重复；
- 测试是否通过同一 Interface 观察行为；
- 正常、失败、取消、损坏和回归路径是否覆盖；
- Trace 和错误是否足以定位问题且不泄漏敏感数据；
- 新依赖、配置和抽象是否由真实需求证明。

### 5. 工程验收与学习验收

工程验收和学习验收是两条独立状态：

- **工程验收**：代码、自动测试、静态检查、集成或 Live 验证、安装验证和独立评审通过。
- **学习验收**：学习者完成模块图、数据流、方案比较、故障实验、Eval 解读、闭卷答辩和延迟复测。

工程验收通过但学习出口未完成时，可以记录为 `Implemented（学习出口待执行）`，不得宣称整个
学习模块完成。人工学习出口必须由学习者本人完成，AI 只能核对证据和追问。

### 6. 关闭与恢复入口

模块关闭时同步更新当前状态、文档索引、README、评审处置和学习记录。未知项必须标明：

- 当前解释；
- 证据边界；
- 需要的最小实验；
- 触发复审的条件；
- 是否阻塞下一模块。

## 边界收拢规则

- 每个版本只交付一个核心端到端结果；辅助能力必须直接服务该结果。
- 先定义最小可验证纵向切片，再扩展规模、Provider、存储或 UI。
- Eval 是所有模块的横向能力，不要求单独占用一个产品版本，但不得后补。
- 先保留可人工检查的小型固定数据集，再扩大到真实和开放数据。
- Session 历史、外部知识、长期记忆和单轮 Context 必须有不同的不变量和所有者。
- 不把框架或库的使用本身当作学习目标；必须能解释它隐藏了什么、失败在哪里以及何时不该使用。
- 不因模仿 Claude Code 或其他项目而复制目录和模块；参考只能提供证据和候选方案。
- 当前版本的工程与学习出口未达到批准门禁前，不启动下一实质性模块。

专项裁定：项目所有者于 2026-09-23 在
[v0.4 访谈 Q23](../plans/v0.4-tool-execution-design-discussion.md) 确定，v0.3 → v0.4 的工程
启动门禁按实际依赖划分；无关 RAG 缺口独立跟踪，影响工具执行、权限、Session 或基础回归
的遗留问题仍须在相关实现前处理。本例外不豁免 v0.4 新回归、设计批准或学习出口，不自动
适用于其他版本，也不将 v0.3 工程状态改为验收通过。

## 模块完成定义

只有同时满足以下条件，模块才可被记为完整学习交付：

- 需求、非目标、架构和决策状态明确；
- 产品能力通过已批准验收；
- 最小 Eval 有实现前基线与实现后对照；
- 关键失败模式已经实际制造并解释；
- 实现与文档通过相称的独立评审；
- 学习者能闭卷重建主数据流、Trade-off 和限制；
- 延迟复测通过，或未通过项进入后续学习计划；
- 当前状态和恢复入口已更新。
